# VX NCI IV — ChatGPT-style MVP Build Plan

**Status:** Planning baseline  
**Target:** A responsive web application that reproduces the familiar ChatGPT interaction pattern while using original VX NCI IV branding and independently implemented code.  
**Parent company:** LUXORA CLUB  
**Working branch:** `develop/vxnci-foundation`

This document is a build plan, not evidence that the listed features have been implemented.

## 1. Product definition

The first release should feel familiar to ChatGPT users:

- A left sidebar for starting chats and reopening recent conversations.
- A central conversation area with user and assistant messages.
- A message composer with send, multiline input, and disabled/loading states.
- Assistant responses generated by a real model through a secure server-side integration.
- A clean, responsive layout for desktop and mobile browsers.

VX NCI IV will use its own name, logo, visual identity, code, and service configuration. It will not use OpenAI's private code, impersonate ChatGPT, or claim to be an OpenAI product.

## 2. MVP scope

### Must work in the first usable release

1. **Chat interface**
   - Start a new conversation.
   - Send a text message and receive a real AI response.
   - Show clear loading and error states.
   - Keep the conversation readable on narrow screens.

2. **Conversation handling**
   - Display user and assistant messages in order.
   - Give each conversation a title.
   - Start a fresh chat without mixing it with the previous chat.
   - Preserve recent chats in the browser for the first MVP, with a clear notice that browser-local history is not account-synced.

3. **Useful response controls**
   - Copy a response.
   - Retry a failed response.
   - Stop generation if the chosen provider and implementation support cancellation.

4. **Secure model connection**
   - Call the AI provider only from a server-side endpoint.
   - Read API credentials from environment variables.
   - Never place provider secrets in browser code, commits, logs, or public configuration.
   - Show a useful setup message if no provider key is configured.

### Explicitly out of scope for the first MVP

- User accounts and cross-device chat synchronization.
- Voice conversations and speech generation.
- Image generation or image understanding.
- File uploads and document analysis.
- Web browsing/search.
- Long-term cross-chat memory.
- Autonomous agents and software-building workflows.
- Payments, subscriptions, and paid model usage.

These can be added after the text-chat foundation is working and tested.

## 3. Proposed technical direction

The following is a provisional implementation choice, not a completed setup:

- **Frontend:** Next.js with TypeScript and a responsive component system.
- **Styling:** Tailwind CSS or equivalent utility-based styling.
- **Server endpoint:** Next.js server route for model requests.
- **Model integration:** A provider adapter so the app is not locked to one model vendor.
- **Initial model provider:** Choose a free-tier provider only after checking current access, limits, data terms, and key setup. Gemini or an OpenRouter free model are candidates; neither is connected yet.
- **Initial history storage:** Browser-local storage/IndexedDB.
- **Source control:** GitHub repository `gabrieltonny394-maker/vxnci-iv`, development on `develop/vxnci-foundation`; keep `main` stable.

Do not assume a database or authentication service is available. Select persistent cloud storage only when account sync is actually being implemented and its cost/security implications are approved.

Keep provider-specific request/response code behind a small adapter. UI components should not know provider API keys or vendor-specific secret configuration.

## 5. First development backlog

### Phase 0 — Foundation

- [ ] Confirm the chosen free-first model provider and its current terms/limits.
- [ ] Create the web application scaffold on the development branch.
- [ ] Add responsive base layout and VX NCI IV visual identity.
- [ ] Add environment-variable example file containing names only, never real secrets.
- [ ] Add setup instructions and a basic run/build check.

**Done when:** The app starts locally, builds successfully, and the empty chat screen works on desktop and mobile.

### Phase 1 — Chat interface

- [ ] Build sidebar with New Chat and recent conversation list.
- [ ] Build conversation view and message bubbles.
- [ ] Build multiline composer and send interaction.
- [ ] Add loading, empty, and error states.
- [ ] Add mobile sidebar behavior and keyboard accessibility.

**Done when:** A user can create a conversation and exchange messages with a temporary local/mock response while the interface is being tested. Mock responses must be clearly treated as development-only.

### Phase 2 — Real AI response

- [ ] Define provider-neutral message and response types.
- [ ] Implement one provider adapter on the server.
- [ ] Add a server-side chat endpoint with input validation and safe error handling.
- [ ] Support streaming if the selected provider and hosting environment allow it.
- [ ] Add cancellation/stop behavior where supported.
- [ ] Verify that the browser never receives the provider secret.

**Done when:** A configured provider returns real responses through the server endpoint, errors are handled, and no secret appears in client bundles or Git history.

### Phase 3 — Chat history and controls

- [ ] Save and load conversations in browser-local storage.
- [ ] Generate editable conversation titles.
- [ ] Add copy response and retry controls.
- [ ] Add delete/clear controls with confirmation.
- [ ] Test refresh and browser restart behavior.

**Done when:** Recent chats persist in the same browser and can be reopened without messages crossing between conversations.

### Phase 4 — Quality and release

- [ ] Test small screens, desktop widths, keyboard navigation, and screen-reader labels.
- [ ] Test empty input, long messages, provider errors, network loss, and repeated sends.
- [ ] Add rate/size limits to the server endpoint.
- [ ] Review privacy notice and data handling.
- [ ] Document deployment steps and verify a real deployed build before announcing a release.

**Done when:** Core flows pass the test checklist and the deployed version is verified end to end.

## 6. Security, privacy, and cost rules

- Never commit API keys, passwords, tokens, or service-role credentials.
- Keep secrets server-side and use a local environment file excluded from Git.
- Do not enable paid services, paid model calls, subscriptions, or billing without explicit approval.
- Check the provider's current free-tier limits and data-use terms before connecting it.
- Do not send sensitive personal information to a model provider unless its data terms are understood and accepted.
- Validate message length and request shape on the server; add abuse/rate controls before public deployment.
- Explain that browser-local history stays in that browser and can be lost when site data is cleared.

## 7. Definition of a truthful MVP

The MVP may be called working only after all of the following are demonstrated:

1. The application starts and builds without errors.
2. A user can start a chat and send a message.
3. A real model response returns through the secure server endpoint.
4. A failed request produces a useful error without crashing the interface.
5. Conversation history can be reopened after refresh.
6. The experience works at desktop and mobile widths.
7. No API secret is exposed in the browser or committed to the repository.

Until then, describe the work as planning, scaffold, prototype, or partial implementation as appropriate.

## 8. Immediate next action

Start Phase 0 by choosing the implementation environment and confirming the free model provider. Then create the application scaffold on `develop/vxnci-foundation`. Do not modify `main`, configure paid services, or add real credentials without explicit approval.
